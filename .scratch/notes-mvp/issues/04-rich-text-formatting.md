# 04 — Rich-text formatting via TenTap (WYSIWYG)

**What to build:** Replace the plain text input from ticket 03 with `@10play/tentap-editor`, and add a formatting toolbar covering every mark in the spec's Extended tier: multiple heading levels, bold, italic, underline, bulleted list, numbered list, and checklist/checkbox. Formatting applies and renders immediately (WYSIWYG) — no markdown syntax is ever typed or shown. Content continues to persist through the same repository content field from ticket 02/03; the derived-title logic (first line of content) continues to work against the richer document format.

**Blocked by:** 02, 03

**Status:** done

- [x] Note editor uses TenTap instead of a plain text input
- [x] Toolbar (or equivalent UI) applies: heading (multiple levels), bold, italic, underline, bulleted list, numbered list, checklist/checkbox
- [x] Applying a mark shows its effect immediately in the editor — no markdown syntax appears anywhere
- [x] Checklist items can be checked/unchecked directly in the editor
- [x] Formatted content round-trips correctly through autosave: closing and reopening a Note preserves all applied formatting
- [x] Derived title (first line) still resolves sensibly against rich content (e.g. a heading as the first line becomes the title)

## Comments

Implemented in `app/note/[id].tsx` (editor screen), `lib/notes/rich-text.ts` (new — the plain-text/document reconciliation layer), `lib/notes/autosave.ts` and `db/repository.ts` (updated to use it).

- **Editor**: `app/note/[id].tsx` now renders TenTap's `<RichText>` + the library's default `<Toolbar>` (unmodified `DEFAULT_TOOLBAR_ITEMS`, which already covers every mark this ticket asks for — bold, italic, underline, heading 1–6 via its own submenu, bulleted/numbered list, checklist — plus a few extras from `TenTapStartKit`, e.g. link/code/blockquote/strike/undo/redo, kept rather than filtered out since building a custom filtered toolbar would mean depending on `DEFAULT_TOOLBAR_ITEMS`' array *order*, which isn't part of the library's public contract). Native `@10play/tentap-editor`/`react-native-webview` linking was already in place from ticket 01.
- **Storage format**: content is stored as a JSON-serialized ProseMirror document (`editor.getJSON()` → `JSON.stringify`), matching ADR-0001's "rich-text JSON document" consequence, in the same `notes.content` text column from ticket 02 — no schema change. `lib/notes/rich-text.ts` is the one place that reconciles this with ticket 03's plain-text notes: `toPlainText` walks a ProseMirror doc into one line per block (or passes plain text through unchanged), `toEditorContent` does the reverse for seeding the editor (wrapping legacy plain text as one paragraph per line — handing TenTap a raw string instead would have it parsed as HTML, silently collapsing every line onto one), and `firstNonBlankLine` extracts what `deriveTitle` shows. `deriveTitle` (repository.ts) and the blank/empty checks (`autosave.ts`'s `isBlank`) both route through `toPlainText` now, since TenTap never persists a literal empty string for an empty document — it round-trips as a document with no visible text (e.g. a lone empty paragraph node), which the old `content.trim().length === 0` check would have missed. `searchNotes` computes `toPlainText` once per note and reuses it for both the title and body checks, so rich-text notes are matched on visible text rather than raw JSON syntax (e.g. searching "bulletlist" no longer false-positives on the node-type keyword).
- **Content flows through the editor asynchronously now** (`onChange` → `editor.getJSON()`, a WebView bridge round trip), unlike ticket 03's synchronous `onChangeText`. Two guards keep this correct: `changeSeqRef` discards an out-of-order response if calls ever resolved out of issue order, and `isUnmountedRef` stops a keystroke's in-flight response from re-scheduling a save after the screen has already left and enqueued its leave decision (which could otherwise update-or-error against a Note the leave decision just deleted). An earlier version of the leave-time decision tried to re-fetch fresh content from the editor on unmount as an extra safety net; removed after tracing React's lifecycle — the WebView's ref is already detached by the time a passive-effect cleanup runs, so that call could only ever time out. The last keystroke's `onChange` round trip being lost if the user navigates away before it resolves is consequently an accepted, inherent limitation of bridging to a WebView-hosted editor, not something this ticket solves.
- **Theming**: the editor's WebView background/toolbar follow the app's light/dark scheme via TenTap's `theme` option; the note body's own text color and the placeholder ("Start typing…", replacing ticket 03's `TextInput` placeholder) need separate CSS injected into the document itself, baked into `bridgeExtensions` for the WebView's first paint and re-injected via `editor.injectCSS` on later theme changes. Gated on RichText's `onLoad` (not mount), and keyed off a load-generation counter rather than a one-shot flag, since `injectCSS` silently no-ops before the WebView has actually loaded and TenTap's `RichText` deliberately remounts the WebView once on iOS right after its first load.
- Test suite additions: `lib/notes/__tests__/rich-text.test.ts` (new — `toPlainText`/`toEditorContent` against rich-text docs, nested lists, checklists, hard breaks, blank-line preservation, and malformed/non-array `content` defensively degrading rather than throwing), plus rich-text cases added to `lib/notes/__tests__/autosave.test.ts` and `db/__tests__/repository.test.ts` (including a search test asserting rich-text notes match on visible text, not JSON structure). 61/61 tests passing; `tsc --noEmit` and `eslint` both clean. Screens remain untested per ticket 03's precedent (no component-testing library set up; the seam that needed coverage — `toPlainText`/`toEditorContent`/`deriveTitle`/`isBlank` — is pure and tested).
- Ran `/code-review` repeatedly (multiple single-angle and one multi-angle pass) against the diff before committing, fixing everything that surfaced: legacy plain text handed to TenTap as raw HTML instead of a document (silently collapsing line breaks); the unmount/async-race issues above; a `docToPlainText` bug double-counting newlines for list/checklist items nested one level, and a second bug that then over-corrected and collapsed genuine blank lines between paragraphs, and a third where a mid-paragraph hard break followed by more text merged onto the next block's line; `searchNotes`'s body check left on raw JSON after `deriveTitle`'s was fixed to use `toPlainText`; a missing placeholder and missing dark-mode theming (regressions vs. ticket 03, now restored); the iOS double-`onLoad` gating gap; unmemoized `toEditorContent`/JSON re-parsing per render; and a malformed-document crash risk in the tree walker. Deliberately deferred (noted, not fixed): `searchNotes` re-parsing every note's content per call rather than caching a plain-text projection — no UI calls it yet (that's ticket 06's job); and the theoretical (bounded to ticket 03, whose plain-text UI this ticket fully replaces) ambiguity where a legacy plain-text Note's literal content could coincidentally parse as `{"type":"doc",...}`-shaped JSON and be misread as an empty rich-text document.
