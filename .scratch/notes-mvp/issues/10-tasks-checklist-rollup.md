# 10 — Tasks: checklist rollup across every Note

**What to build:** A Tasks screen that gathers every checklist item (`taskItem`) from every Note into one list, grouped by the Note it came from, so to-dos scattered across notes are visible in a single place. Ticket 04 gave checklists to the editor, but a checked item is only ever visible inside the Note that holds it. Each row shows the item's text, its checked state, and which Note (and Folder) it lives in; tapping opens that Note; toggling checks or unchecks it and writes back into the Note's document.

**Blocked by:** 04. Overlaps with 09 — both add a bottom-nav destination, so whichever lands second reuses the other's `NavSection` change rather than redoing it.

**Status:** done

## Implementation notes

- **Shape it like ticket 06.** `withFolderContext` in `lib/notes/search.ts` is the precedent: a pure module composed over the repository's existing queries, rather than a new repository method. Do the same here — a new `lib/notes/tasks.ts` over the existing `listNotes()`. Checklist extraction is a content concern, and `notes.content` is opaque to SQL (ADR-0001), so there's no query to push it into.
- **Two functions:** `extractTasks(content)` walks the document for `taskItem` nodes and returns `{ index, text, checked }`, and `setTaskChecked(content, index, checked)` returns the updated JSON. Both are pure and both are what the tests target.
- **Build on `rich-text.ts`, don't reimplement it.** It already knows `taskItem` (it's in `LINE_BREAK_TYPES`), and already owns `ProseMirrorNode`/`ProseMirrorDoc`, `parseDoc`, `toDoc`, and the tree walker. TipTap's TaskItem carries its state in `attrs.checked`. A second, subtly different traversal idiom in a new file is exactly the bug factory ticket 04's comment history describes.
- **Item identity**: a `taskItem` node has no id, so address items by document-order ordinal, derived by the same traversal both functions use. Legacy plain-text Notes (pre-ticket-04) contain no task items at all — extraction should degrade to an empty list rather than throw, the way the rest of `rich-text.ts` degrades on malformed input.
- **Stale-write risk**: toggling rewrites the Note's whole content. If that Note changed after this screen loaded it, an ordinal can address a different item than the user tapped. Re-read the Note's current content immediately before toggling and re-derive from that, rather than trusting the copy the list is rendering.
- **`updatedAt`**: `updateNoteContent` bumps it, so ticking a box from Tasks reorders Home's most-recently-edited list. That's arguably correct (it is an edit) but it's a visible side effect of a screen the user may think of as read-only. Pick one, and say which in the comment.
- **Nested task items**: TenTap allows nesting checklists. Flattening them into one list is fine for a first pass — just make it a stated decision, along with whether an unchecked child under a checked parent needs to read differently.
- **Vocabulary**: CONTEXT.md currently only knows these as "checkbox/checklist" under **Formatting mark**. If "Task" becomes user-visible vocabulary, add it to the glossary as its own term — otherwise name the screen "Checklists" and stay with the existing word. Don't introduce a synonym silently; CONTEXT.md's *Avoid* lists exist for exactly this.

## Non-goals

Standalone to-dos that don't live inside a Note, due dates, reminders or notifications, and reordering items across Notes. (Extends `.scratch/notes-mvp/spec.md` past the MVP pass; it does not revise it.)

## Comments

Implemented in `lib/notes/tasks.ts` (new — the pure seam), `components/tasks/tasks-list.tsx` (new), `app/tasks.tsx` (new), plus the bottom-nav/route/glossary changes listed below. This ticket landed before 09, so it introduced the third `NavSection` itself.

- **Seam shape** follows ticket 06 as planned: `lib/notes/tasks.ts` is pure, React- and repository-free, and composes over the repository's existing `listNotes`/`listFolders` rather than adding a query — `notes.content` is opaque to SQL (ADR-0001), so checklist items can only be found by walking the document. The screen literally chains ticket 06's seam into this one: `collectTasks(withFolderContext(notes, folders))`, so the Folder-name logic is reused rather than re-derived.
- **One walk, not two.** `extractTasks` and `setTaskChecked` both go through a single `mapTaskItems`, which is what assigns ordinals — reading and writing can't disagree about numbering if they never number separately. `rich-text.ts` gained one small export for this, `nodeToPlainText`, so an item's own label is projected by the same `docToPlainText` that projects a whole Note rather than by a second traversal that re-derives what a "line" is.
- **A bug the tests caught**: the first version called the visitor *after* recursing into a node's children, so ordinals were right (parent before child) but the collected list came back child-first for nested checklists — a nested item would render above its parent, and `extractTasks(...)[0]` wasn't the first task in the document. Fixed by visiting a node before walking its children, which makes both the ordinals and the visit order document order.
- **Item text** excludes any checklist nested inside the item (those are separate rows with their own ordinals) and flattens hard breaks onto one line, since a row shows one line. An item with no text at all is kept, not dropped, and renders as "Empty item" — dropping it would silently hide a real checkbox.
- **Nested checklists are flattened** into the same list rather than indented, per the ticket's "fine for a first pass". A child of a checked parent reads no differently; nothing in the model says a parent's state constrains its children's.
- **Toggling** re-reads the Note through `getNote` immediately before writing rather than trusting the copy the list is rendering — a task's ordinal is only meaningful against the document it came from, and that document may have been edited or dictated into since this screen last loaded. `setTaskChecked` returns its input unchanged when the ordinal addresses nothing, and the screen treats that as "resync", never as success. (The same unchanged return also covers "the stored state already matched", where a resync is equally correct.)
- **`updatedAt` decision (the ticket asked for one)**: a toggle goes through `updateNoteContent` and bumps `updatedAt`, so the Note moves up Home's most-recently-edited order. Accepted rather than worked around — ticking a checkbox really does change the Note's stored content, and a second "update that doesn't count as an update" repository path would put the repository at odds with the Note's own model for a cosmetic reason. Recorded in CONTEXT.md's resolved behaviors so it reads as a decision rather than a side effect.
- **Ordering and the optimistic update**: `collectTasks` floats open items above completed ones within each group (each still in document order), and Notes keep `listNotes`' most-recently-edited order. Toggling updates local state in place *without* re-sorting — re-sorting on tap would yank the row out from under the finger that just tapped it — so a ticked item stays put until the next focus reload. Each row carries its document ordinal, so the display sort never has to be reconciled with what `setTaskChecked` addresses (there's a test pinning exactly that).
- **Not a `NoteCard`**: task rows are a different shape of row — a checkbox is a second, in-place action on content *inside* the Note, where every `NoteCard` list only ever opens a Note. `TasksList` shares `Card`, the eyebrow/title treatment, and the fixed bottom padding for the floating nav, but not the card itself.
- **Vocabulary**: the screen is user-visible "Tasks", so **Task** is now a CONTEXT.md glossary term (one checklist item, always inside exactly one Note, no due date/reminder/assignee, identified only by position), with *Avoid: to-do, reminder, checklist* — checklist is the group, a Task is one item in it.
- **Tests**: `lib/notes/__tests__/tasks.test.ts` (new, 21 cases) covers extraction (flat, nested, multi-line, missing `checked` attr, empty item, prose-only, ticket 03 plain text, empty content, malformed non-array `content` degrading rather than throwing), toggling (right item only, nested ordinals, other attrs/text preserved, out-of-range and negative ordinals returning input unchanged, plain text never rewritten as JSON), and grouping (notes without checklists dropped, note order preserved, open-before-completed with ordinals surviving the sort, extra note fields carried through). 116/116 tests passing, `tsc --noEmit` clean, `eslint` reporting only the two warnings that pre-date this ticket.
- **Not verified on device/simulator**: the checks above are the test suite, typecheck, and lint. Nothing here was exercised in a running dev client, and per spec.md UI/component-level tests remain out of scope, so the screen itself (layout, checkbox tap targets, empty state) has not been seen running.
